Card-skimming code was hidden in product descriptions across Jumbo, Disco and Vea. I found it while building a price comparison tool.

Había código para robar tarjetas escondido en las descripciones de productos de Jumbo, Disco y Vea. Lo encontré mientras armaba un comparador de precios.

How I found it

SmartCart compares grocery prices across Argentine supermarkets, so its scraper reads every field of every product, descriptions included. One of the stores was Vea, a Cencosud chain running on VTEX, with over 20,000 products per sweep. Some of its descriptions contained obfuscated JavaScript instead of text. The same code was in many products in Cencosud's other stores, Jumbo and Disco.

Checking before reporting

Obfuscated code proves nothing on its own: analytics and tag managers look similar. Three things settled it:

  1. What it did: once deobfuscated, it captured card data entered at checkout.
  2. Where it was: a description field, where nothing legitimate runs code.
  3. How far it reached: many products across three stores, so it was injected on purpose.

I stopped there: no test orders and no contact with the server receiving the data.

Re-running the scraper let me measure the cleanup product by product, which is how the last five turned up. SmartCart was never affected, because it stores descriptions as plain text. Vea is back in the app, off by default and with a warning.

Lessons for store owners

  • Rich-text fields are an attack surface. Sanitize description HTML when saving it and when rendering it.
  • Use a strict Content Security Policy. Blocking inline scripts and unknown destinations stops this kind of skimmer even after it's injected.
  • Monitor what the page runs, not just what you deploy. This code never went through a code review.

skimwatch

Finding the next one shouldn't depend on luck, so I built skimwatch, a Go crawler that flags code injected into store catalogs and runs nightly on GitHub Actions. Its first pass was a passive scan of Argentine VTEX stores, reading only public catalog APIs and page source.

1stored XSS found

The hit was a stored XSS on a bank-owned marketplace. An outside seller's product listing started with a <script> tag that the site served unescaped, so it ran with each visitor's session on the bank's site. It looked like a proof of concept, but it could have been swapped for a real payload at any time. I reported it to the bank on 3 Nov 2026.

The wider finding: every store scanned renders description HTML unfiltered, and almost none send a Content Security Policy.

Cómo lo encontré

SmartCart compara precios entre supermercados argentinos, así que su scraper lee todos los campos de cada producto, descripciones incluidas. Una de las tiendas era Vea, una cadena de Cencosud que corre sobre VTEX, con más de 20.000 productos por pasada. Algunas descripciones tenían JavaScript ofuscado en lugar de texto. El mismo código estaba en muchos productos de las otras tiendas de Cencosud, Jumbo y Disco.

Verificar antes de reportar

El código ofuscado por sí solo no prueba nada: la analítica y los tag managers se ven parecidos. Tres cosas lo confirmaron:

  1. Qué hacía: desofuscado, capturaba los datos de tarjeta ingresados al pagar.
  2. Dónde estaba: en un campo de descripción, donde nada legítimo ejecuta código.
  3. Hasta dónde llegaba: muchos productos en tres tiendas, así que fue inyectado a propósito.

Ahí paré: ni compras de prueba ni contacto con el servidor que recibía los datos.

Volver a correr el scraper me permitió medir la limpieza producto por producto, y así aparecieron los últimos cinco. SmartCart nunca estuvo afectado, porque guarda las descripciones como texto plano. Vea volvió a la app, desactivada por defecto y con un aviso.

Lecciones para quien tenga una tienda

  • Los campos de texto enriquecido son superficie de ataque. Hay que sanitizar el HTML de las descripciones al guardarlo y al mostrarlo.
  • Usar una Content Security Policy estricta. Bloquear scripts inline y destinos desconocidos frena este tipo de skimmer aunque ya esté inyectado.
  • Vigilar lo que la página ejecuta, no solo lo que se despliega. Este código nunca pasó por una revisión.

skimwatch

Encontrar el próximo no debería depender de la suerte, así que construí skimwatch, un crawler en Go que marca código inyectado en catálogos de tiendas y corre todas las noches en GitHub Actions. Su primera pasada fue un escaneo pasivo de tiendas argentinas sobre VTEX, leyendo solo las APIs públicas de catálogo y el código fuente.

El hallazgo fue un XSS almacenado en el marketplace de un banco. Un producto de un vendedor externo empezaba con una etiqueta <script> que el sitio servía sin escapar, así que se ejecutaba con la sesión de cada visitante en el sitio del banco. Parecía una prueba de concepto, pero podía cambiarse por un payload real en cualquier momento. Se lo reporté al banco el 3 de noviembre de 2026.

El hallazgo general: todas las tiendas escaneadas muestran el HTML de las descripciones sin filtrar, y casi ninguna envía una Content Security Policy.

Los payloads, los detalles de ofuscación, a dónde se enviaban los datos y el nombre del marketplace quedan afuera a propósito.
