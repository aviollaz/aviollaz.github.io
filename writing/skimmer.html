Card-skimming code was sitting in product descriptions across Jumbo, Disco and Vea. I wasn't looking for it. I was building a price comparison tool.

Había código para robar tarjetas escondido en las descripciones de productos de Jumbo, Disco y Vea. No lo estaba buscando: estaba armando un comparador de precios.

Why I was reading product HTML at all

SmartCart finds the cheapest way to fill a grocery cart across Argentine supermarkets. Scrapers run on a schedule, products get matched across stores with vector search, and a constraint solver splits the cart to spend as little as possible.

Vea, a Cencosud chain, was one of the stores. Its catalog runs on VTEX, and the scraper pulled every field of every product from it, descriptions included: over 20,000 products per sweep. Descriptions are supposed to be marketing copy: ingredients, sizes, a sentence or two about the product. Some of Vea's came back with something else in them.

What was in the descriptions

The text field contained executable, obfuscated JavaScript. It wasn't one careless listing. The same code appeared across many products, and checking Cencosud Argentina's other stores turned it up there too: Jumbo, Disco and Vea all carried it.

That pattern mattered more than any single snippet. One odd description is a seller's mistake. The same payload across three stores' shared catalogs points to something injected deliberately, at scale.

Being sure before saying anything

Obfuscated code on a store page is not proof of an attack. Analytics, A/B testing and tag managers all ship minified, hard-to-read scripts. Before reporting, I wanted solid answers to three questions:

  1. What does it do? Once deobfuscated, its purpose was to capture payment card data entered by shoppers.
  2. Does it belong there? No. Product descriptions are content, not code. Nothing legitimate needs to run from that field.
  3. How far does it reach? Three stores and many products, not one page or one careless listing.

Once all three pointed the same way, I stopped investigating. I didn't place test orders or interact with whatever was receiving the data. The goal was to be certain enough to report, not to poke at live infrastructure.

Disclosure

I reported it privately and published nothing until the code was gone.

Having the scraper made one part easy: I could re-run it and measure the cleanup, product by product, instead of taking anyone's word for it. That's how the five stragglers showed up after most of it was gone.

SmartCart itself was never a carrier. It flattens every description to plain text before storing it, because rendering a third party's HTML hands them your page. Vea came back to the app afterwards, but off by default, with a warning users see before turning it on.

Why something like this goes unnoticed

The injection point was content, not code. Security reviews tend to watch a site's own JavaScript and its dependencies. Product descriptions are treated as data: edited by many people, stored in a CMS, and rendered as HTML on every product page. Three takeaways for anyone running a store:

  • Rich-text fields are an attack surface. If a description can carry a <script>, eventually one will. Sanitize on save and on render.
  • A strict Content Security Policy is cheap insurance. Blocking inline scripts and unknown destinations breaks this class of skimmer even after it's injected.
  • Watch what the page actually runs, not just what you deploy. The code that ran in shoppers' browsers here never went through a code review.

Looking for the next one: skimwatch

I found this one by accident, because a side project happened to read every product page. That seemed like a bad way to rely on finding the next one, so I built skimwatch: a Go crawler that reads store catalogs and flags code injected into product content. It runs nightly on GitHub Actions and keeps its results in Postgres.

Its first full pass was a passive scan of Argentine stores running on VTEX: reading their public catalog APIs and page source, nothing more.

The one hit was a stored XSS on a bank-owned marketplace. A product listing uploaded by an outside seller started with a <script> tag, and the site served it unescaped, so it ran in the browser of anyone who opened the page, with their session on the bank's site. The payload looked like a proof of concept, but whoever uploaded it could swap it for a real one at any time. I reported it to the bank on 3 Nov 2026, with the evidence and concrete fixes.

The broader result worries me more than the single hit. Every store in the scan renders description HTML without filtering it, and almost none send a Content Security Policy. Nothing stops the next skimmer except nobody having tried yet.

The hard problem is false positives: legitimate tools inject and obfuscate scripts all the time. Telling a tag manager from a skimmer is the part I'm still refining, and the part I find most interesting.

I've deliberately left out the payloads, how they were obfuscated, where they sent data, and which marketplace had the XSS. This post is about how the problems were found and handled, not a recipe for repeating them.

Por qué estaba leyendo el HTML de los productos

SmartCart busca la forma más barata de llenar un carrito entre supermercados argentinos. Los scrapers corren de forma programada, los productos se emparejan entre tiendas con búsqueda vectorial y un solver de restricciones reparte el carrito para gastar lo menos posible.

Vea, una cadena de Cencosud, era una de las tiendas. Su catálogo corre sobre VTEX, y el scraper traía todos los campos de todos los productos, descripciones incluidas: más de 20.000 productos por pasada. Las descripciones deberían ser texto de marketing: ingredientes, tamaños, una o dos frases sobre el producto. Algunas de las de Vea traían otra cosa.

Qué había en las descripciones

El campo de texto tenía JavaScript ejecutable y ofuscado. No era un producto mal cargado: el mismo código aparecía en muchos productos, y al revisar las otras tiendas de Cencosud Argentina apareció también ahí. Jumbo, Disco y Vea lo tenían.

Ese patrón importaba más que cualquier fragmento suelto. Una descripción rara es un error de carga. El mismo código en los catálogos compartidos de tres tiendas indica algo inyectado a propósito y a escala.

Estar seguro antes de decir nada

Que haya código ofuscado en una tienda no prueba un ataque. Las herramientas de analítica, de A/B testing y los tag managers usan scripts minificados y difíciles de leer. Antes de reportar quería respuestas firmes a tres preguntas:

  1. ¿Qué hace? Desofuscado, su objetivo era capturar los datos de las tarjetas que ingresaban los compradores.
  2. ¿Corresponde que esté ahí? No. Las descripciones son contenido, no código. Nada legítimo necesita ejecutarse desde ese campo.
  3. ¿Hasta dónde llega? Tres tiendas y muchos productos, no una página o un error aislado.

Cuando las tres respuestas apuntaron para el mismo lado, dejé de investigar. No hice compras de prueba ni interactué con lo que recibía los datos. El objetivo era estar lo bastante seguro para reportar, no tocar infraestructura en producción.

Tener el scraper facilitó una parte: podía volver a correrlo y medir la limpieza producto por producto, sin depender de la palabra de nadie. Así aparecieron los cinco productos que quedaban cuando casi todo ya se había ido.

SmartCart nunca fue un portador. Convierte cada descripción a texto plano antes de guardarla, porque renderizar el HTML de un tercero es entregarle tu página. Vea volvió a la app después, pero desactivada por defecto y con un aviso antes de activarla.

Por qué algo así pasa desapercibido

El punto de inyección fue el contenido, no el código. Las revisiones de seguridad suelen mirar el JavaScript propio del sitio y sus dependencias. Las descripciones se tratan como datos: las editan muchas personas, se guardan en un CMS y se muestran como HTML en cada página de producto. Tres conclusiones para quien tenga una tienda:

  • Los campos de texto enriquecido son superficie de ataque. Si una descripción puede llevar un <script>, tarde o temprano alguna lo va a llevar. Hay que sanitizar al guardar y al mostrar.
  • Una Content Security Policy estricta es un seguro barato. Bloquear scripts inline y destinos desconocidos frena este tipo de skimmer aunque ya esté inyectado.
  • Hay que mirar lo que la página ejecuta, no solo lo que se despliega. El código que corría en los navegadores de los compradores nunca pasó por una revisión.

Buscando el próximo: skimwatch

Este lo encontré por casualidad, porque un proyecto personal leía todas las páginas de productos. No parecía una buena forma de depender de encontrar el próximo, así que construí skimwatch: un crawler en Go que lee catálogos de tiendas y marca código inyectado en el contenido de los productos. Corre todas las noches en GitHub Actions y guarda los resultados en Postgres.

Su primera pasada completa fue un escaneo pasivo de tiendas argentinas sobre VTEX: lectura de sus APIs públicas de catálogo y del código fuente de las páginas, nada más.

El único hallazgo fue un XSS almacenado en el marketplace de un banco. Un producto cargado por un vendedor externo empezaba con una etiqueta <script>, y el sitio la servía sin escapar, así que se ejecutaba en el navegador de quien abría la página, con su sesión en el sitio del banco. El código parecía una prueba de concepto, pero quien lo cargó podía cambiarlo por uno real en cualquier momento. Se lo reporté al banco el 3 de noviembre de 2026, con la evidencia y correcciones concretas.

El resultado general me preocupa más que el hallazgo puntual. Todas las tiendas del escaneo muestran el HTML de las descripciones sin filtrar, y casi ninguna envía una Content Security Policy. Lo único que frena al próximo skimmer es que nadie lo haya intentado todavía.

El problema difícil son los falsos positivos: herramientas legítimas inyectan y ofuscan scripts todo el tiempo. Distinguir un tag manager de un skimmer es la parte que sigo afinando, y la que más me interesa.

Dejé afuera a propósito los payloads, cómo estaban ofuscados, a dónde mandaban los datos y qué marketplace tenía el XSS. Este texto cuenta cómo se encontraron y se manejaron los problemas, no es una receta para repetirlos.
