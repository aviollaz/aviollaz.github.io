I found a card skimmer while scraping grocery prices

Obfuscated card-skimming code was sitting in product descriptions across Jumbo, Disco and Vea. I wasn't looking for it. I was building a price comparison tool.

Why I was reading product HTML at all

SmartCart finds the cheapest way to fill a grocery cart across Argentine supermarkets. Scrapers run on a schedule, products get matched across stores with vector search, and a constraint solver splits the cart to spend as little as possible.

Vea, a Cencosud chain, was one of the stores. Its catalog runs on VTEX, and the scraper pulled every field of every product from it, descriptions included: over 20,000 products per sweep. Descriptions are supposed to be marketing copy: ingredients, sizes, a sentence or two about the product. Some of Vea's came back with something else in them.

What was in the descriptions

The text field contained executable, obfuscated JavaScript. It wasn't one careless listing. The same code appeared across many products, and checking Cencosud Argentina's other stores turned it up there too: Jumbo, Disco and Vea all carried it.

That pattern mattered more than any single snippet. One odd description is a seller's mistake. The same payload across three stores' shared catalogs points to something injected deliberately, at scale.

Being sure before saying anything

Obfuscated code on a store page is not proof of an attack. Analytics, A/B testing and tag managers all ship minified, hard-to-read scripts. Before reporting, I wanted solid answers to three questions:

  1. What does it do? Once deobfuscated, its purpose was to capture payment card data entered by shoppers.
  2. Does it belong there? No. Product descriptions are content, not code. Nothing legitimate needs to run from that field.
  3. How far does it reach? Three stores and many products, not one page or one careless listing.

Once all three pointed the same way, I stopped investigating. I didn't place test orders or interact with whatever was receiving the data. The goal was to be certain enough to report, not to poke at live infrastructure.

Disclosure

I reported it privately and published nothing until the code was gone.

Having the scraper made one part easy: I could re-run it and measure the cleanup, product by product, instead of taking anyone's word for it. That's how the five stragglers showed up after most of it was gone.

SmartCart itself was never a carrier. It flattens every description to plain text before storing it, because rendering a third party's HTML hands them your page. Vea came back to the app afterwards, but off by default, with a warning users see before turning it on.

Why something like this goes unnoticed

The injection point was content, not code. Security reviews tend to watch a site's own JavaScript and its dependencies. Product descriptions are treated as data: edited by many people, stored in a CMS, and rendered as HTML on every product page. Three takeaways for anyone running a store:

  • Rich-text fields are an attack surface. If a description can carry a <script>, eventually one will. Sanitize on save and on render.
  • A strict Content Security Policy is cheap insurance. Blocking inline scripts and unknown destinations breaks this class of skimmer even after it's injected.
  • Watch what the page actually runs, not just what you deploy. The code that ran in shoppers' browsers here never went through a code review.

What I'm building because of it

I found this one by accident, because a side project happened to read every product page. That seemed like a bad way to rely on finding the next one.

So I'm building SkimWatch: a crawler that scans online stores every night for client-side attacks like this one. A few early decisions:

  • Narrow before wide. The whole pipeline, from crawl to detection to alert, works end to end on a small set of stores before I add more. A detector that's never been tested on real pages is worth less than broad coverage of nothing.
  • Go. Crawling many pages concurrently is the core workload. It's also a language I wanted to learn, and a real project is the best way.
  • Boring infrastructure. Nightly runs on GitHub Actions, results in Postgres on Neon. It's the setup SmartCart's scrapers already ran on, so I know where it breaks.

The hard problem is false positives: legitimate tools inject and obfuscate scripts all the time. Telling a tag manager from a skimmer is the part I'm still working out, and the part I find most interesting.

I've deliberately left out the payload, how it was obfuscated, and where it sent data. This post is about how the problem was found and handled, not a recipe for repeating it.
